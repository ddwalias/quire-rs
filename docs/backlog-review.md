# Backlog review: product scope, sequencing and QA

Reviewed 2026-10-27. All 121 existing Kaneo items were read with their full descriptions, parentage and relationships and checked against the current repository, architecture, quality strategy and QA operating plan. Two missing product deliverables were added, bringing the backlog to 123 items. This is a planning review, not runtime validation or a completed product acceptance report.

Live verification passed: descriptions, priorities, hierarchy and blocker relationships match the reviewed plan; the resulting dependency graph is acyclic.

## Assessment

The capability areas are useful, but the previous backlog was not an execution-ready release specification. Several dependencies reflected an assumed implementation order instead of a real prerequisite. Numerical families did not enumerate what "selected" meant. Release documentation followed qualification, and integrated engineering acceptance and first-use guidance had no clear owners.

The revised backlog distinguishes enabling work, discovery, candidate features, optional integrations and historical baselines. Candidate tickets become implementation-ready only after their finite scope, required contracts and acceptance cases are recorded. Completing an investigation cannot imply that its corresponding feature works. M1/M2/M3 remain provisional sequencing labels until QUI-13 records a release allocation.

## Corrections

- Updated 116 open items; retained the five completed baseline records and their documented limitations.
- Removed 76 false or premature blocking relationships and added 31 required ones. Removed blockers are retained as related work so their context is preserved.
- Quire schema changes and recovery no longer wait on Prime import. Current native smoke, accessibility, IME, font/DPI, parser fuzzing and performance checks can start before future editors, plots or importers.
- Async revision safety can wrap the existing full evaluator; headless services do not require incremental evaluation. Scientific families no longer inherit unrelated worksheet feature prerequisites.
- QUI-13 now owns a finite v1 product contract with intended users, required workflows, platforms, file modes, exclusions and named acceptance scenarios.
- QUI-18 owns requirement-to-ticket coverage and gap closure; QUI-106 owns the function inventory and finite family scopes; QUI-118 owns actual QA case execution evidence.
- QUI-100 prepares the release scope manifest and compatibility notes before QUI-121 qualifies a candidate. Prime writing is required only for a release that explicitly selects it.
- Added QUI-122 for integrated engineering/user acceptance and QUI-123 for getting-started and supported-feature guidance. Candidate qualification consumes both.

## Remaining readiness conditions

The review does not choose unresolved product preferences or claim every original Mathcad behavior has been discovered. QUI-13 still needs a recorded release scope decision. QUI-106 must enumerate confirmed worksheet functions and resolve finite selected variants. Large family deliveries need concrete child slices where the selected scope is too broad for one increment. Staffing, estimates and dates remain unset until scope and ownership support them.

Required supported-platform cases need actual results; configured CI and written checklists do not count as execution. Reproducible manual observations remain valid while capture/replay and native automation are developed, but they do not complete those automation tickets. See [the QA operating plan](qa-plan.md).

## Recommended next work

Start QUI-13 (product contract) and QUI-116 (feature verification process). In parallel, reproduce the evidence inventory and establish current-product QA baselines rather than wait for new functionality. Use QUI-106/18 to turn the selected contract into a covered, finite delivery backlog and QUI-118 to connect it to executed acceptance cases. Select implementation slices after this readiness check.
